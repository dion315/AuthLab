Rejects an existing provider session older than this, forcing a fresh authentication.

Sent as the OIDC claims parameter — the standard way to ask for a specific claim or authentication context rather than hoping the provider volunteers it. Two shapes worth knowing:

{"id_token":{"acr":{"essential":true,"values":["mfa"]}}} demands an authentication context. {"id_token":{"groups":null,"auth_time":{"essential":true}}} asks for optional claims by name. Whatever arrives is listed in full on the dashboard, so start there to find the names your provider uses.

Token security

Off by default because each needs matching configuration at the provider, and a half-configured one fails in ways that read as a broken connection.

Adds offline_access to the request, which is what actually makes a provider issue one — and the provider must also allow that scope and the refresh_token grant for this client. The dashboard then offers a Refresh action, which is how you find out whether policy is re-evaluated at refresh time or only at sign-in.

Providers that rotate on use return a replacement and invalidate the old one immediately. Untick to keep the original deliberately and watch the second refresh fail — which is what a stolen, replayed refresh token looks like from the provider's side.

Signs a proof of possession into a DPoP header on every token request. The provider binds the access token to that key's thumbprint in its cnf.jkt claim, so a stolen token is useless without the key. A keypair is generated when you save and kept afterwards, so the thumbprint stays stable. The dashboard shows whether the provider actually bound the token or ignored the proof.

Publishes an encryption public key for the provider to fetch and encrypt to. Register the JWKS URL below as this client's jwks_uri. Support varies — Okta and Ping offer it, Entra does not for OIDC, and several providers accept the setting and send an unencrypted token anyway. A plain signed token is still accepted, and the dashboard says which one actually arrived.

Many applications authorise against groups a provisioning connector pushed them rather than against anything in the token: the token says who you are, the directory sync says what you can do. Choosing a SCIM source lets you test that whole loop — provision into a group, sign in, gain the role, remove from the group, lose it.

SCIM matching uses userName, email, and externalId. If your subject claim is sub it is a pairwise identifier that will never match a UPN — point it at preferred_username or email instead.
